## 结论

**M1 能稳定跑满 60 FPS**，且各项指标都在预算内。当前场景（分块地形 + 1400 棵树 + 阴影 + 泛光）作为起点是安全的。

**但有两个必须注意的信号：**

1. **三角形数（357k）已经很接近 400k 预算**，而且这是在视距 320 米下测的。把视距拉到 512 米以上就会突破预算。后续加内容时，三角形的余量是最紧的一项。

2. **帧率被垂直同步锁在 60**，四个用例的数值几乎完全一致（p95 都是 16.80ms）。这说明 **GPU 还有余量，但测不出余量有多少**——真实上限需要加大负载才能压出来。

## 本次测量的局限（重要）

这些数字不能直接外推到真实游玩场景，原因有三：

1. **devicePixelRatio = 1**。真实 MacBook 屏幕是 Retina（dpr = 2），填充率是本次的 **4 倍**。填充率恰恰是 M1 最吃紧的资源。真实 Retina 下必须靠「分辨率倍率」调节（面板里可调），不能想当然认为能跑 60。

2. **JS 堆 ≠ 总内存占用**。`performance.memory` 只统计 JS 对象，**不包含 GPU 侧显存中的几何与纹理**。39MB 只能说明 JS 侧没有泄漏，不能代表整页内存。要看真实占用得用 Chrome 任务管理器（Shift+Esc）。

3. **headless 窗口尺寸固定**，没有覆盖全屏与不同长宽比的情况。

**因此：这份基线用于「代码没有性能回归」的对比，不作为「真实游玩体验」的结论。** 真实基线请在打开的浏览器里点「▶ 开始自动巡检」重测一次。

## 下一步建议

- 在**真实 Retina 分辨率**下测一次，确定合适的分辨率倍率（预期要降到 0.75–1.0）
- 做一次**压力探索**：把视距拉到 512、树木拉到 3000，找出帧率跌破 30 的临界点，据此确定世界的最大规模
- 阶段 1 加入角色控制器后，重点观察「贴地高速飞行」用例的 p95 帧时间——地形流式加载的卡顿会最先在这里暴露

**真实浏览器（推荐，数字最可信）**

```bash
cd client && npm run build && npm run preview
```

打开页面 → 点右上角「▶ 开始自动巡检」→ 结束后「⬇ 导出报告」。

**自动化回归（headless，用于 CI 或改动后快速比对）**

```bash
cd client && npm run dev          # 另开一个终端
cd .. && node tools/verify_bench.mjs "http://localhost:5173/?bench=1&delay=3000" 80
```

> 注意：不要用 Chrome 的 `--virtual-time-budget` 跑巡检。虚拟时钟推得太快，
> 而巡检依赖 requestAnimationFrame 的真实时间轴，结果是页面只跑几帧、巡检永远走不完。
> `tools/verify_bench.mjs` 用 CDP + 真实时间等待，就是为了绕开这个坑。

## 阶段 2 复测

阶段 2 同时做了两类改动，都必须复测：

1. **地形参数修正**：山脊强度 0.72 → 0.86，全球高差从 51 米提到 70 米量级。
   地形形状变了，可见几何的分布也跟着变。
2. **新增内容**：水体（一个大平面 + 逐像素波浪）、昼夜循环（含月光平行光）、风动植被。

| 用例 | avg FPS | DrawCall 峰值 | 三角形峰值 |
|---|---|---|---|
| 地平线远眺 | 60.0 | 77 | 271k |
| 森林穿行 | 60.0 | 86 | 281k |
| 高空俯瞰 | 60.0 | 92 | 334k |
| 贴地高速飞行 | 60.0 | 80 | 279k |

**总评**：最低 avg FPS 60.0 · DrawCall 峰值 92 · 三角形峰值 334k · JS 堆峰值 39 MB

### 结论

**没有退化，指标反而更优**。对比阶段 0 基线：DrawCall 峰值 109 → 92，三角形峰值 357k → 334k。

原因是地形起伏变大后山体遮挡更有效，视锥剔除剔掉了更多物体——这比任何渲染优化都划算。代价是新增了一个 draw call（水面）和多一盏平行光（月光），完全被上述收益盖过。

**局限与之前相同**：devicePixelRatio 为 1（真实 Retina 是 4 倍填充率）、JS 堆不含显存、帧率被垂直同步锁在 60 因而测不出余量。天气与水面在真实分辨率下的实际开销，需要在真实浏览器里重测。

## 阶段 3 复测

阶段 3 加入了体力系统、角色状态机（攀爬/滑翔/游泳）与陡崖地形层。

| 指标 | 阶段 2 | 阶段 3 |
|---|---|---|
| 最低 avg FPS | 60.0 | 60.0 |
| DrawCall 峰值 | 92 | 92 |
| 三角形峰值 | 334k | 334k |
| JS 堆峰值 | 39 MB | 40 MB |

**结论：零代价。** 体力系统与状态机是纯逻辑运算（每帧几十次浮点比较），不产生任何渲染开销；陡崖地形只改变高度分布、不增加几何量。唯一的变化是 JS 堆 +1MB（新增的状态与配置对象）。

角色行为回归 13 项、移动机制验证 15 项同样全部通过，出生点仍稳定落在原点、海拔 20.6 米。

## 阶段 4 复测

加入元素引擎（火焰点燃、蔓延、上升气流、灼烧伤害）与 8 只敌人。

| 指标 | 阶段 3 | 阶段 4 |
|---|---|---|
| 最低 avg FPS | 60.0 | 60.0 |
| DrawCall 峰值 | 92 | 141 |
| 三角形峰值 | 334k | 337k |
| JS 堆峰值 | 40 MB | 50 MB |

**结论：仍然零代价。** DrawCall 从 92 涨到 141 主要是 8 只敌人（每只 6 个部件），与元素系统无关——火焰用 InstancedMesh，实测 142 个燃烧格子只占 **1 个 draw call**。元素传播按 4 Hz 而非每帧推进，逻辑开销也可以忽略。

战斗系统 10 项、元素系统 11 项断言全部通过。

## 关于"帧率锁在 30"的判读方法

阶段 4 末尾的一次复测里，四个用例的帧率齐刷刷变成 30.0（min 29.9 / max 30.1）。这不代表性能退化，判断依据有三条：

1. **抖动量级不对**。性能不足时帧率会剧烈波动（例如 22–48），而这次抖动只有 0.2，是浏览器在无法稳定 60 时把 rAF 主动节流到 30 Hz 的特征。
2. **几何负载完全没变**。DrawCall 144、三角形峰值 337k，与上一次测量逐项一致。如果真是渲染变慢，这两项会先起变化。
3. **宿主负载高**。当时 `load average` 为 3.7，且 ZCode 自身占满一个核，再叠加用户的其他应用——测的是整机抢 CPU 的结果，不是游戏的开销。

**结论：遇到"整齐的 30 或 60"先怀疑环境，遇到"波动的中间值"才是性能问题。** 真要确认渲染瓶颈，看 DrawCall 与三角形数是否变化比看 FPS 更可靠。
