# 网页版塞尔达式开放世界

一个运行在浏览器里的低多边形开放世界游戏，目标是《旷野之息》式的探索与元素互动体验。

**当前阶段：阶段 4 进行中——元素引擎已实现火与冰：点燃草地、按风向蔓延、上升气流托举滑翔；冻结水面搭出可行走的冰桥，冰又会被火烤化。**

---

## 先读这个：为什么是这个技术路线

完整的论证见 [开发规划.md](./开发规划.md)，这里只留三条决定性结论：

**1. 远程 GPU 帮不上实时渲染的忙；两台远程机器的网络条件差异极大。**

游戏跑在浏览器里，只能用**本机 GPU**，远程机器不参与画面渲染。实测两台机器的对比：

| 机器 | 网络路径 | 往返延迟 | 带宽 |
|---|---|---|---|
| 5060 Ti | Tailscale 中继（本机出口旧金山、机器出口香港，且校园网锐捷设备干扰 DERP） | 320–480 ms（波动大） | **5.3 KB/s** |
| 4090 服务器 | 教育网公网直连 | **84 ms** | **2.6 MB/s** |

5060 Ti 的 5.3 KB/s 相当于拨号上网——下载 gzip 后 155KB 的 JS 要 29 秒，所以它既做不了渲染串流，也托管不了游戏。而 4090 走国内公网直连，带宽是它的 500 倍，**做静态托管完全够用**（但 84ms 仍不够渲染串流，那个需要 < 30ms）。

不过无论部署在哪都要记住：**部署位置不影响画质**——网页游戏在哪个浏览器打开，就用哪台机器的 GPU 渲染。远程 GPU 的核心价值在**离线计算**（地形生成、资产烘焙），原则是 **「离线重算力，运行时轻渲染」**。

> 5060 Ti 上已部署一份构建产物（`~/zelda-game/`，含零依赖的 Python 静态服务器）作为归档，但实测不可用。停止它：`ssh gpu5060 'pkill -f serve.py'`。

**2. 真正的瓶颈是 8GB 内存，不是 GPU 算力。**
本机 MacBook Air M1（7 核 GPU / 8GB 统一内存）：系统占约 3GB、Chrome 占 1–1.5GB，留给游戏页面的安全预算是 **1.2–1.5GB**。所以贴图要压缩、模型要精简、世界要分块流式加载。内存管理是第一优先级的工程约束，不是优化项。

**3. 3D 是必需品，低多边形是唯一现实路线。**
攀爬、滑翔、火势蔓延这些核心机制全部依赖三维空间。而《旷野之息》本身就是低多边形加手绘质感——「低模 + 好光照 + 好配色」就能达到接近的观感，恰好是 M1 扛得住的。

## 快速开始

```bash
cd client
npm install
npm run dev
```

打开 <http://localhost:5173>。

**操作**：`WASD` 移动 · `Shift` 奔跑（耗体力）· `空格` 跳跃，**空中再按一次展开滑翔伞** · **鼠标左键点击或 `J` 攻击** · **`F` 点燃身前草地** · **`R` 冻结周围水面** · **`G` 食用背包里的果子** · 走向陡坡**自动攀爬** · 入水**自动游泳** · 鼠标拖拽转视角 · 滚轮拉近拉远 · `H` 开关性能信息。

**游戏内按左下角的 `?` 按钮有完整玩法说明。**

几个值得试的组合：

- 点一片草地，等火势铺开，爬上山坡展开滑翔伞飞过火场——上升气流会把你托起来
- 走到湖边按 `R` 冻出一条冰桥走过去；想拆桥就在岸边点火，火会一路把冰烤化
- 往水边跑可以切断追着你的火线（水面不可燃）

出生点周围散布着 8 只小怪，靠近它们会被发现并追击。

右上角面板可实时调整分辨率倍率、阴影、泛光、视距、树木数量、时刻与风力。关掉面板里的「角色模式」会切到自由飞行（`WASD` 平移、`Q/E` 升降、`Shift` 加速），用于取景调试与性能巡检。

| 参数 | 作用 |

| `?hour=18.4` | 设定起始时刻（0–24），用来看日出日落与夜景 |
| `?freeze=1` | 冻结时间推进，便于对比不同时段 |
| `?bench=1&delay=6000` | 加载后自动开跑性能巡检 |

## 阶段 0：性能摸底怎么用

这一阶段的目的是回答一个问题：**M1 到底能跑多少？** 结论将决定后续所有画质目标的取舍，所以测量必须可复现、可存档，而不是靠"感觉挺流畅"。

### 自动巡检

点右上角 **「▶ 开始自动巡检」**，相机会依次跑过四个典型场景，每段录制 8–10 秒：

| 用例 | 在测什么 |
|---|---|
| 地平线远眺 | 可见地形块最多，三角形与 draw call 峰值 |
| 森林穿行 | 植被叠加地形，阴影投射体最多 |
| 高空俯瞰 | 视锥几乎全在渲染，填充率与顶点双高 |
| 贴地高速飞行 | 考验地形流式加载，最容易出卡顿 |

跑完后点 **「⬇ 导出报告」** 保存数据，里面包含 fps 的 avg/min/p95、帧时间、draw call、三角形数、JS 堆内存，以及环境信息（GPU 型号、实际渲染分辨率、阴影与泛光开关状态）。

也可以用 URL 参数无人值守地跑：

```
http://localhost:5173/?bench=1&delay=6000
```

### 通过标准（Gate）

- **帧率**：四个用例的最低 avg FPS ≥ 30
- **内存**：JS 堆峰值 ≤ 1200 MB

不通过就下调画质目标（降低分辨率基准、缩短视距、植被改公告板），而不是继续往上堆效果。

> **注意**：`npm run dev` 下测得的数字会偏低（未压缩、带 sourcemap）。做正式基线记录时请用 `npm run build && npm run preview`。

### 当前基线（M1 / 8GB，1280×720，视距 320 米）

| 机位 | FPS | Draw | 三角形 | JS 堆 |
|---|---|---|---|---|
| 游玩（第三人称） | 60 | 148 | 572K | 98 MB |
| 草原中景 | 60 | 166 | 515K | 97 MB |
| 高空俯瞰 | 60 | 164 | 514K | 70 MB |

对照规划里的预算（60 FPS / DrawCalls < 300 / 三角形 < 400K / 纹理 < 400MB / 内存 < 1.5GB）：**draw call 和内存都有大幅余量，三角形超了约 43%**。

这个超出是有意接受的。400K 是在手写几何时期定的——那时树只有两种、林相稀疏，地面只有顶点色。现在同样的三角形买到的是密集得多的森林、分块跟随的草场，以及铺满地面的花与灌木，而帧率仍然是稳定的 60（M1 的瓶颈不在顶点填充率）。数字里的三角形还包含阴影 pass 的重复绘制（关掉阴影会掉到约一半），实际场景约为其中的六成。

如果以后要压回 400K，按性价比排序：先收阴影相机半径（当前 55 米）、再收草场的覆盖半径（当前 ±88 米，视野外的块不进管线但仍在内存里）、再降草被密度、最后才动散布物数量——那是唯一会直接影响观感的一项。

## 项目结构

```
游戏/
├── client/                    # 浏览器游戏（Vite + TypeScript + Three.js）
│   ├── public/assets/
│   │   ├── models/            # 角色与敌人（KayKit，CC0）
│   │   └── nature/            # 植被与道具（Kenney Nature Kit，CC0）
│   ├── src/
│   │   ├── core/              # 主循环、性能监控、输入
│   │   ├── render/            # 渲染管线、天空（"怎么画"）
│   │   ├── terrain/           # 高度场、分块地形与 LOD
│   │   ├── entities/          # 敌人 AI 与外观（手写 / 骨骼两套 rig）
│   │   ├── gameplay/          # 角色控制、战斗、体力、背包、角色外观
│   │   ├── physics/           # 障碍物空间索引
│   │   ├── ui/                # HUD、小地图、大地图、帮助面板
│   │   ├── world/             # 世界内容（"画什么"）：散布、素材库、元素网格
│   │   └── benchmark/         # 阶段 0 场景、自动巡检、参数面板
│   └── dist/                  # 构建产物
├── tools/                     # 离线内容管线（Python，跑在远程 GPU 上）
├── server/                    # 预留：NPC 对话代理
└── 开发规划.md                 # 完整技术规划与路线图
```

**分层原则**：`render/` 只管「怎么画」，`world/` 只管「画什么」，玩法逻辑独立。将来从 WebGL2 切到 WebGPU，改动应局限在 `render/` 内。

## 已实现的内容

### 阶段 0：世界与性能基线

- **分块地形 + 四叉树式 LOD**：以关注点为中心按环形范围加载，四级顶点密度（64/32/16/6 段），带裙边遮住 LOD 接缝
- **程序化高度场**：分形噪声 + 山脊噪声，按海拔与坡度实时混合生物群系顶点色
- **烘焙式散布植被**：每区块把所有物种（树、灌木、岩石、花草）合并成一个静态网格，森林斑块分布，每个实例有色调浮动
- **风格化渐变天空**：亮度可控的渐变球，带日盘与光晕，跟随相机
- **阴影**：单级方向光阴影，阴影相机跟随关注点，覆盖周围 70 米
- **性能监控**：实时 HUD + 自动巡检 + 可导出的统计报告

### 阶段 1：能走的地形

- **角色控制器**：重力、地面吸附、跳跃、可行走坡度限制。坡太陡时沿**等高线滑行**而不是硬停，玩家不会撞上看不见的墙
- **手感细节**：土狼时间（离地后仍可短暂起跳）与跳跃缓冲（落地前按跳跃会记住）
- **第三人称相机**：帧率无关的指数平滑跟随、镜头与地形之间的自动拉近（防穿地）、滚轮缩放
- **角色表现**：有四肢与关节的低多边形人形（头、尖耳、头发、束腰外衣、腰带、靴子、佩剑）。走路时四肢交替摆动、手臂与同侧腿反向，攀爬时四肢张开抓握，滑翔时双臂上举抓伞
- **帮助面板**：左下角 `?` 按钮，含完整操作与玩法说明；`Esc` 或点击空白处关闭
- **小地图**：左下角圆形地图，显示地形、敌人（红点）、火（橙点）、冰面（白点）与玩家朝向。地形底图**分帧采样**（一次扫 4 行）——按 64×64 一次采完要跑四千多次噪声查询，会造成肉眼可见的卡顿；按时间节流而非按帧，帧率下降时底图不会跟着变慢
- **拾取与背包**：地上散布着野莓（回 1 颗心）与向阳果（回 2 颗心），走近自动拾取。按 `G` 进食；生命已满时不会浪费果子。物品定义集中在 `ITEM_DEFS` 一张表里，加新物品只需加一行
- **武器挂点**：剑挂在**右手枢轴之下**而不是挂在根节点上。挂在根节点时位置写死，手臂摆动而剑纹丝不动，看起来像悬在身体旁边硬跟着平移；挂进手臂后挥砍完全由手臂驱动，不再需要单独给剑编一套轨迹
- **控制模式切换**：面板里可在「角色模式」与「自由飞行」之间切换，后者用于调试取景与性能巡检

### 阶段 2：世界外观

- **水体**：波浪法线、菲涅尔反射、阳光碎光。不做几何起伏——水面要覆盖整个视距，顶点位移需要极密的网格才看得出效果，改用逐像素解析的波浪法线，两个三角形就能撑起整片水域
- **昼夜循环**：太阳方位、光色、天光、雾色、水面反射色全部由**太阳高度角**这一个变量派生，改一处就整体一致。含日出日落的暖色、夜间星空与月光
- **月光**：夜里专用的方向光。只用半球光做夜景会得到一团灰——半球光色与草地顶点色都是暗色，相乘后趋近于黑，没有明暗对比就读不出地形轮廓
- **风动植被**：顶点着色器注入的风摆，相位取自实例世界坐标，整片森林不会同步摆动
- **地貌分带改为相对水位**：调水位或地形尺度时配色会自动跟着走，不需要重新标定一堆绝对高度

### 阶段 3：探索循环

- **体力系统**：攀爬、冲刺、游泳、滑翔共享同一个体力池。这是塞尔达式设计的**核心约束机制**——有了它，地形才真正成为关卡：想抄近路直接爬崖，就得赌体力够不够
- **攀爬**：走向陡坡自动切换，不消耗按键。移动用**坡面参考系**（W 沿梯度向上、A/D 沿等高线），而不是相机参考系——后者会让玩家在仰视崖壁时按 W 却往水平方向走
- **滑翔**：空中再按一次跳跃展开伞，恒定缓慢下降，水平速度反而比跑步快
- **游泳**：入水自动切换，按跳跃上浮。体力耗尽会下沉，但只会沉到固定深度并缓慢回复，不会溺死——避免"游到一半必死"的挫败
- **陡崖地形**：用窄区间 smoothstep 在台地边缘造出真正的崖壁（约 1.2% 的地表需要攀爬）。纯噪声生成的地形天然"顺滑"，最高只有 45°，永远触发不了攀爬
- **体力环 HUD**：放在角色下方而不是角落，因为攀爬时眼睛盯着角色，体力环必须在余光范围内。满体力自动淡出
- **姿态表现**：滑翔时展开伞面、攀爬时身体前倾贴向崖面、游泳时只露出上半身

### 阶段 3：战斗与敌人

- **近战攻击**：鼠标左键（拖拽仍是转视角，靠"按下时长 + 位移"区分）或 `J` 键。攻击做成一条时间轴——前摇 → 命中判定 → 后摇，按下立刻造成伤害的战斗会退化成无脑连点
- **扇形命中判定**：只比较水平方向。带上高度差的话，站在坡下砍不到坡上的敌人，玩家会觉得"明明够得着却打不中"
- **敌人 AI**：idle / chase / attack / hurt / dead 状态机。警戒范围与脱战范围分开设置，否则玩家在边界徘徊时敌人会一步一停地抖动
- **受击反馈**：闪红、击退、硬直。没有硬直就无法用连续攻击压制敌人，战斗会变成互相对拼血量
- **生命值与无敌帧**：玩家 6 颗心，受击后有 0.9 秒无敌并闪烁。没有无敌帧，一次接触会在连续几帧里反复结算，玩家瞬间暴毙
- **死亡与重生**：倒下后留 1.6 秒让玩家看清自己是怎么死的，再传送回出生点
- **敌人不会刷在水里或陡坡上**——玩家够不着，敌人自己也会卡住

### 阶段 4：元素引擎（火）

- **点燃与蔓延**：按 `F` 点燃身前的草地。火会自行向八个方向的邻居扩散，**顺风方向的邻居更容易被点燃**，火线因此拉成椭圆而不是正圆
- **按 tick 推进**：蔓延每 0.25 秒判定一次（4 Hz），不是每帧。为每个燃烧格子查询邻居，每帧跑一遍在火场铺开后会吃掉整个帧预算；4 Hz 在观感上完全够用，代价降到 1/15
- **可燃性由地形决定**：草地可燃，水面、沙滩、裸岩、陡坡、雪线以上点不着。火势因此被地形自然约束——**往水边跑能切断火线**
- **上升气流**：火堆上方产生上升气流，滑翔经过时会被托起（实测从常态 -2.2 m/s 的下降到 +4.26 m/s 的爬升）。这是元素引擎与滑翔系统的接点，"点火 → 气流 → 飞得更高"这个组合是成立的
- **灼烧伤害**：站在火里会掉血，敌人也一样。玩家的无敌帧天然充当了灼烧的冷却，不需要额外计时器
- **确定性随机**：蔓延用固定种子的伪随机，火势可复现，验证脚本的断言才稳定

### 阶段 4：元素引擎（冰）

- **冻结水面**：按 `R` 把周围的水面冻成冰，形成可行走的冰桥（消耗体力——能搭桥过河的能力不该免费）
- **站上冰面**：不给状态机加任何特例。冰面只是"地形之上的一层额外表面"，控制器多查一次高度就自然站上去了，游泳状态会自动退出
- **火能融冰**：燃烧的格子会烤化相邻的冰。**这是元素之间的第一条克制关系**——冰能搭桥过河，火能把桥拆掉
- **互斥规则**：正在燃烧或刚烧过的地面冻不上，所以"先放火再冻水"是无效操作
- **渲染**：每格一块薄板，一整片冰仍是一个 draw call。材质带自发光，否则冰面会和深色水面糊在一起看不清边界

### 阶段 5：换成开源美术素材

手写几何体拼角色的路子走到头了——一个球加几根柱子，无论再加多少零件，比例、关节过渡和面部都做不出来。这一阶段把主角、敌人、植被全部换成 CC0 的开源素材。

**素材来源**（都是 CC0，可自由商用）：

| 用途 | 素材包 | 内容 |
|---|---|---|
| 主角 | [KayKit Adventurers](https://github.com/KayKit-Game-Assets/KayKit-Character-Pack-Adventures-1.0) | 4 个低多边形角色，每个 76 段动画 |
| 敌人 | [KayKit Skeletons](https://github.com/KayKit-Game-Assets/KayKit-Character-Pack-Skeletons-1.0) | 4 种骷髅，95 段动画 |
| 植被 | [Kenney Nature Kit](https://kenney.nl/assets/nature-kit) | 329 个模型：树、灌木、岩石、花草、蘑菇 |

- **主角是「林克化」的盗贼**。KayKit 的 Rogue_Hooded——绿兜帽、绿束腰外衣、棕色皮带短靴——是这套素材里最接近林克的一身（同包的 Knight 是全罩板甲，Mage 是长袍）。只有肤色要改：原始素材是深棕肤色，而贴图是纯色块图集，按颜色距离做替换即可，不会糊掉边界
- **暗色块的替换有个必踩的坑**：`new Color(hex)` 会做 sRGB→线性转换，而 canvas 里的像素是 sRGB 编码的，两边直接比永远匹配不上、改色静默失效。要拆字节比较，或显式跳过颜色管理
- **敌人用骨骼驱动，而不是播预录动画**。Enemy 的状态机是实时算摆动角的（受击侧倾、出招前扑、待机呼吸），改用现成动画就得重写整套状态机。所以给每根要驱动的骨头配一个空 pivot，Enemy 照旧写 `armL.rotation.x`，pivot 上的旋转每帧被乘进骨骼的局部旋转里；骨架自己循环播 Idle 保证站姿自然
- **这个叠加有个必踩的坑：基准旋转必须每帧先从绑定姿势复位**。Idle 只驱动了部分骨骼，`chest`、`upperarm` 这些在它里面根本没有轨道——不复位的话，上一帧叠加出来的结果会被当成这一帧的基准，摆动角于是逐帧累加，几秒钟后骷髅的脑袋就甩到身体外面去了。正确顺序是**复位到绑定姿势 → 播动画 → 记录基准 → 设摆动 → 叠加**
- **量身高要逐顶点问蒙皮后的位置**。`Box3.setFromObject` 会把 41 根骨骼连同 IK 控制器一起算进去；几何体包围盒量的是绑定姿势（T 字张开、手臂上举）。两个都不对——按前者缩放骷髅会矮一头。正确做法是先推一帧 Idle 让骨架摆成站姿，再对每个 SkinnedMesh 调 `getVertexPosition()` 求蒙皮后的真实体积
- **模型尺度差了 4 倍**。Kenney 那套是按「桌面摆件」做的，树只有 1–2 米。加载清单里显式写明每个模型该有多高，靠包围盒自动放大是行不通的——那样灌木会被拉成树、树会被压成灌木
- **配色要重新映射，不能直接用**。Kenney 的原色是给俯视小场景配的：树叶青绿、树皮浅粉棕、石头近乎纯白。放进地形只会显得发灰发脏，所以按材质名（`leafsGreen` / `woodBark` / `stone`…）统一映射到本项目的调色板
- **平滑着色，不是平面着色**。手写树只有 100–200 面且形状规整，平面着色能把棱面变成风格；Kenney 的树冠是球体锥体拼的，轮廓本来就是圆的，再按面着色就成了一颗颗多面体骰子

### 阶段 6：主线剧情

有了角色、敌人、元素引擎，还缺一件把这一切串起来的东西——**玩家为什么要在乎这片大陆**。这一阶段补上一条完整的主线，从醒来走到通关大约需要二十分钟。

**流程**：在草原醒来 → 营地里的贤者交代来龙去脉 → 三座元素祭坛（火 / 冰 / 风，顺序随意）→ 集齐封印后封印之门开启 → 击败暗蚀骑士 → 世界恢复。

**关键设计**：

- **三座祭坛没有先后**。主线可以是一条线，但线要挂在玩家自己走过去的地方，而不是"必须先去 A 再去 B"。任务栏永远指向最近的那枚未收集封印，但你去哪座都行
- **能力门槛代替文字锁**。冰之祭坛在湖心沙洲、风之祭坛在扫描到的最高处——能不能到，取决于你会不会用冻结水面和攀爬滑翔。不写"需要 XX 能力"的提示，直接把东西放在玩家当下到不了的地方，这是塞尔达式关卡设计的核心手法
- **地标位置是开局扫描出来的**。地形是程序生成的，写死坐标迟早撞上"祭坛悬在半空"。所以按地形条件现场找点：火之祭坛要高处平地、冰之祭坛要挨着水、风之祭坛占最高山头。用「方位角分区 + 打分」而不是直接取极值，否则三个祭坛会挤在同一片高地，跑一趟就全收了。打分以海拔为主、距离只给很小的权重——距离权重大了，所有地点都会收敛到搜索半径的最大值上，一眼就看出是程序生成的
- **每座祭坛是一场要打的仗**，不是走过去点一下。靠近触发守卫战，清完场才给封印——没有这一步，整条主线会退化成跑图
- **对话期间只冻结角色，不冻结世界**。敌人照常行动、火照常烧，否则对话框会变成一个可以拿来做安全屋的无敌时间
- **通关不切场景**。放一段全屏文案，点掉之后继续留在这片大陆上——玩家刚解锁了全部能力，这时候把他踢回主菜单是最亏的做法

**导航**：屏幕上方常驻当前目标与直线距离；小地图上的金色菱形是目标点，出了地图范围会贴边指方向。靠这两样，玩家不需要记住任何一个坐标。

**小地图的箭头一直指着身后**。箭头画成朝上（顶点在 -y），要让它指向角色朝向，转角是 `π - yaw` 而不是 `-yaw`，整整差了一个 π。推一遍：画布 x 向右、y 向下，世界 +X 映射到画布 +x、世界 +Z 映射到画布 +y；角色朝向由 `yaw = atan2(dx, dz)` 定义，所以画布里的方向向量是 `(sin yaw, cos yaw)`，把 `(0,-1)` 顺时针转 θ 得到 `(sinθ, -cosθ)`，令它相等就解出 `θ = π - yaw`。

**岩石在草原上立成了一排棕色小山**。Kenney 的 `rock_*` 是一坨坨**压扁的土丘**——原始尺寸高 0.26、宽 1.02，宽高比接近 4。而加载器当时只会按高度归一化，想要 1.5 米高就会得到 6 米宽。现在给素材清单加了 `fit` 字段，扁平的模型（岩石、石板、原木、篝火圈）按**宽度**归一化。

**斜坡上的物件边缘悬空**。物件是按中心点的地面高度摆的，而它自己有宽度——坡越陡、越宽，边缘翘得越高。现在按"边缘在坡度下会抬高多少"的一半往下沉，压住悬空又不会把整棵树埋进去。

**找水边这一步返工了两次，值得记一笔**。地形实测是这样的：出生点落在一片内陆高地上，**半径 300 米内一滴水都没有**，最近的水在 500 米开外。第一版 `findWaterside` 从水面往里退、退到岸上就算数——一次都没命中，直接落到兜底分支，冰之祭坛被丢在一片内陆草地上，"不冻冰桥就过不去"整个落空。原因是它假设了水域外面紧挨着平缓的岸，而这片地形里水多半被崖壁围着，退多少步都是陡坡。改成逐点评估"这里像不像岸边"之后才找对。然后又发现祭坛虽然在水边，却站在**岸上**——玩家蹚水就过去了，门槛等于没有。最后做成两轮扫描：先找被水环绕的沙洲（周围水域 > 62%），找不到才降级到岸边。现在冰之祭坛落在 500 米外的湖心沙洲上，四周 54% 是水。

### 阶段 7：地表丰富化与画面细化

主线跑通之后，最大的问题是**地面太空**：林子漂亮，但走进去脚下只有草，像一片刚种完树苗的荒地。这一阶段集中解决"单调"，顺带把几个视觉 bug 收掉。

**把散射配比从"树是主角"改成"树占一半"**。原来是按树优先配的权重，1900 个物件里树占了八成，剩下全是零星小石头。重配之后树降到五成，其余让给灌木、花、蘑菇、石头、倒木，总数提到 2800——地被物件面数低（花 76 面、小石头 16 面），加一千个的代价很小。

**草场从"一块固定草地"改成"按块跟随"**。原来是一块 150 米见方的草场落在原点，玩家跑出 75 米就走出草地，脚下突然变回光秃秃的顶点色，而那里离视距边缘还有两百多米——**走着走着草没了，比一开始就没有草更出戏**。现在 44 米一块、5×5 块跟着关注点走，覆盖 176 米。顺带修好了一件事：原来整片草场共用一个 InstancedMesh，包围球覆盖全图，视锥剔除等于没有；分块之后剔除才真正生效，所以总簇数涨了、实际画出来的反而更少。

**草叶从 3 片加到 4 片，每片高度和倾斜都不同**。三片等高等距的叶子看起来像栅栏。叶尖用两种绿交替，一根簇内部就有层次，不必只靠实例色调。

**地表配色加了两层噪声扰动**。生物群系配色是按海拔和坡度算的连续函数，同一片草原会得到一模一样的绿——从空中看像刷了一层漆。大尺度那层摆动色相（干得发黄 / 湿得发青），小尺度那层加颗粒。再加一条按高度走的明暗梯度近似地形自遮挡：低处被周围的山挡掉一部分天光，所以暗一些。真正的环境光遮蔽要在屏幕空间算，M1 上划不来，这条廉价的梯度已经能让山谷和山顶分得开。

**性能**：这一阶段后三角形从 530K 涨到 572K，draw call 148，三机位仍是稳定 60 FPS。涨的部分几乎全在草和地被上，而它们正是"丰富"的来源。

### 阶段 9：动作与交互补完

这一阶段修的全是"能玩但不对劲"的地方——单个看都不致命，凑在一起就是廉价感。

**骨骼名匹配从来没成功过（影响最大的一处）**。GLTFLoader 会把骨骼名里的点剥掉：模型文件里写的是 `upperarm.l`，加载到场景里就成了 `upperarml`。我的关节映射表用的是带点的原名，于是**一根骨头都没匹配上**。而失败是静默的——驱动数组空着，程序化的挥爪和摆腿全部变成空操作。表现就是"骷髅只会平移"和"游泳姿势摆好了但一动不动"。修法是比对前把两边都归一化（去点、去下划线、转小写），找不到时还要明确告警——这种静默失效不该再出现第二次。

**游泳时人竖着插在水里**。姿态是用 `rotation.x`（俯仰）和 `rotation.y`（朝向）分别设的，而 Three.js 的 Euler 默认顺序是 XYZ——先转 yaw 再转 pitch，**pitch 就成了绕世界 X 轴**。角色朝东的时候，一个"前倾"会变成侧翻。改成 `YXZ` 顺序（先绕自身 X 压出俯仰，再整体绕世界 Y 转到朝向），并把游泳的俯仰从 28° 加到 66°，人终于是趴在水面上而不是竖着插进去。

**蛙泳动作**。KayKit 的 76 段动画里一段游泳的都没有，所以角色只有"趴平"没有"划水"。用和敌人同一套办法补：给四肢的根骨骼各留一份基准旋转，每帧把划水的姿态乘上去；手和腿反相（蛙泳是先划手再蹬腿），相位由实际速度驱动。

**骷髅走路是滑行的**。原来只播 Idle、靠腿骨前后摆动模拟走路——脚在原地划水，身体却整体平移。骨架里明明有 `Walking_A` / `Running_A`，现在按速度切换，播放速率也跟着速度走；程序化摆腿只留两成做步伐的摇晃感。顺带修掉朝向：骷髅和主角一样，被那个多余的 180° 补偿搞成了退着追人。

**攻击没有前摇**。原来的时间轴是 0.08 秒前摇 + 0.34 秒总长——按下鼠标那一刻剑已经挥完了，玩家感受不到"我在出招"，只看到敌人掉血。现在前摇 0.2 秒、总长 0.58 秒，攻击动画按这个时长压缩播放（不压缩的话招式还没挥到位就被切回待机，像抽了一下）。敌人的挥爪也从 `sin(t·π)` 那条平滑曲线上改成了两段：前 45% 把手往后收，之后快速劈出——玩家需要"要打你了"的预告。

**石头上能站人了**。障碍物过去只有水平推出，没有任何"顶面"的概念。现在障碍物可以带一个 `topY`，角色控制器多查一次高度就自然站上去了——不需要在状态机里加特例。关键在于这个查询**必须接受脚底高度**：只接受不高于脚底的表面，否则角色走到石头旁边就会被自动抬上去，等于隔空爬石头；跳跃时脚底升到石头之上，下一次查询才成立，于是"跳上去"是跳出来的。同时已经站上去的障碍物不再参与水平推出，不然角色一踩上石头就会被自己的碰撞体推下去。石头、树桩、倒木共 15 个物种标了可站立。

**沙滩上突然长满草**。草场的海拔门槛写的是 `水位 + 0.6 米`，而地形配色要到 `水位 + 4 米`才从沙滩过渡到草地——中间那三米多的沙滩被判成"可以长草"。从远处看岸边是干净的沙，走过去却突然全长满，比一开始就不长草更出戏。门槛对齐到地形分带即可。

**测试的间歇性失败**。连着跑多个测试时后面的会随机挂，机器空闲时又没事。查下来是三件事叠在一起：

1. `waitForBoot` 只等 `window.__world` 存在就返回——而世界建好那一刻，角色往往还在出生的空中往下掉、地形区块才铺开一半。现在它还会等"角色已落地且没有残余垂直速度"
2. headless Chrome 除了主进程还会拉起 renderer、gpu 好几个子进程，只对主进程发 `SIGKILL` 的话那些子进程会留下来继续吃 CPU，跑十几个测试后机器就被拖垮了。改用 `detached` 启动、杀整个进程组
3. **有一次失败其实是我自己把测试改坏了**——加诊断字段时写了重复的变量名，整段注入脚本语法错误，一直返回 null。而我把它归因成了"环境负载"，白排查了好几轮。教训是：测试报错时先看一眼它到底输出了什么，别急着怀疑环境
4. **还有一次是场景里节点重名**。`ModelAvatar` 把场景节点硬编码成 `player-model`，而 NPC 用的是同一个模型类——于是场景里同时存在好几个 `player-model`，`getObjectByName` 只会返回第一个。游戏本身看不出问题（每个模型动自己的），但任何按名字找角色的代码都会摸到一个 NPC。表现是"明明在划水却一动不动"，排查了这个很久。现在名字可配置，NPC 用自己的 `npc-<id>`；测试也改成直接持有角色对象的引用，不再按名字遍历

现在 `tools/run_all.sh` 统一跑全部 14 个脚本，失败会自动重试一次（CI 里对付抖动的常规手段）。重试不会掩盖真问题——真有 bug 的话两次都过不了。

### 阶段 10：战斗反馈与水域体验

**敌人不再叠到玩家身上**。冷却那 1.15 秒里敌人会继续朝玩家推进——`chase` 分支只在"进入攻击距离且冷却完毕"时才切状态，其余情况一律前进。于是敌人一路贴到角色身上叠成一个，看起来像穿模，实际是"没有停步距离"。补上一条：已经在攻击距离内就站定转身。实测最近距离 1.82 米（攻击距离是 2.2）。

**攻击前摇原来被自己削掉了**。前一阶段给骨骼版敌人加了走路动画，顺手把程序化摆腿的幅度压到两成（动画在摆，程序化只留一点摇晃感）。但那个系数把攻击一起套了进去——前摇从 44° 缩到 9°，等于没有。现在攻击走完整幅度，而且直接用骨架自带的挥砍动画，起手、转腰、收招都是现成的，比程序化摆手自然。玩家的出招同理：0.2 秒前摇 + 按出招时长压缩的攻击动画。

**敌人有了头顶血条**。只在挨打之后出现、几秒后淡出——全程挂着一排血条会把草原变成血条展览，也失去"这一下打得疼不疼"的即时反馈。血条挂在管理器的场景节点上而不是敌人身上：敌人节点会跟着 yaw 旋转，挂进去就永远正对不了镜头。

**死亡动画**。原来那套"缩小 + 下沉"是没有动画时的替代方案，套在真实倒地动作上就成了双重表现——人会一边侧倒一边缩进地里，看起来像陷进地面。现在骨架版直接播 `Death_A`，移除时间也等动画播完（2.1 秒）。

**掉落**。骷髅死后掉一块骷髅骨，三成概率再掉一颗野莓。结算放在死亡那一刻而不是倒地动画播完——否则玩家要盯着尸体等两秒才看到东西掉出来。

**游泳时人沉在水下两米**。角色控制器已经把手位停在水面下 0.35 米处（那是角色的原点/脚底），渲染层又压了 1.05 米——两次下沉叠起来，整个人沉到水面以下两米多，从岸上看只剩一团模糊的影子。去掉渲染层那次重复计算即可。

**水太不透明**。基础 alpha 0.72 意味着只有不到三成的光能透过水面，掠射角还会升到 0.98（几乎一堵墙）。风格化的水不需要物理正确的吸收，它要的是"一眼看得到水下有什么"——降到 0.38，掠射角上限收到 0.72。

**游泳涟漪**。没有这一层，游泳看起来像"一个模型贴着水面平移"。一小撮循环复用的圆环，预分配、轮流启用，绝不在运行时 new。

**小地图可以拖动查看，也能打标记**。拖动时底图跟着偏移并描一圈橙边提醒"这不是你所在的位置"，松手 2.6 秒后平滑回中——不自动回中的话，玩家跑一段之后会忘了自己看的不是当前位置。右键打标记，同一处再点一次取消（上限 12 个，超出挤掉最旧的）。

### 阶段 11：垂直移动与姿态补完

**游泳是仰泳，不是俯卧**。绕 X 轴按右手定则转 θ，角色正面朝向从 `(0,0,1)` 变成 `(0, -sinθ, cosθ)`——**θ 为正时 y 分量为负，也就是脸朝下**。上一版写的是 `-1.15`，于是人仰面朝天躺在水里、四肢在水面上划。这个符号我推错过一次，现在把推导写进注释了：`SWIM_TILT` 必须是正值。

**滑翔伞**。一个压扁的四棱锥横撑在头顶（不是圆锥——四棱锥的棱线能把伞面分成几块，风一吹有明暗变化），横向撑开的比例做成连续变量，开合才有过渡而不是啪地出现。用双面材质，否则从下方抬头会看到一片空洞。

**对着树和石头走会开始攀爬**。这是塞尔达式垂直移动的核心：地图上每根柱子都是潜在的路。石头爬到顶能站上去，树爬到树冠下方就停住——站到树冠上是一团叶子，不合理，但爬上去看个视野很值。攀爬时角色被吸附在柱子表面，吸附距离**必须和碰撞推出的距离一致**，比它近的话两者会每帧对着拉。

**攀爬状态抖动**。刚抱住树时人就在地面高度，下一帧"爬到地面了"的判定立刻成立，状态被退回 ground——两个状态每帧来回抖，速度反复清零，表现是**抱着树一动不动**。修法是两处：进入攀爬时先把人抬离地面 0.12 米，以及"触地退出"只在主动向下爬时才判定。

**攀爬触发范围收窄**。一开始判定裕量给了 0.45 米，结果在草原上跑动时会不断被路过的石头和树干吸住，冲刺测试直接卡成 0 速度。现在要求几乎贴住（0.2 米）**且**朝向它（前 60° 内）才算。

### 阶段 12：存档、收集与敌人分层

**存档**。之前刷新页面就是从零开始——对一条二十分钟的主线来说这个代价太大了，玩家打到第二座祭坛时误触刷新，一切归零，之后再也不会打开这个游戏。

用 localStorage 而不是 IndexedDB：一份存档就是几 KB 的 JSON，同步 API 毫无压力，而 IndexedDB 要写一堆异步样板。等以后存档里要放地形改动（会到 MB 级）再换也来得及。

**必须存版本号**。读档时字段对不上会静默地得到一个半损坏的状态（比如任务卡在没有目标的阶段）。版本不匹配就直接丢弃重来——丢掉一次进度，好过让玩家卡在一个走不下去的世界里。

**Quest 的读档是"重放"而不是"赋值"**：不直接写 `stage`，而是按存档重放"收集封印 → 和贤者对话 → 开门 → 击败 Boss"这几个动作。这样任何一条不变量都由正常游玩那套代码保证，读档和玩下去不会走出两个不同的状态。

顺带记一个测试上的坑：**验证存档不能开两个浏览器实例**。`cdp.mjs` 每次 launch 都用独立的 user-data-dir 并在关闭时删掉，两个会话之间 localStorage 完全不共享——那样测的是"换了台电脑还记不记得"。必须用同一个实例 `Page.reload`，才等价于玩家按 F5。

**宝箱**。主线只有三座祭坛和一条通往 Boss 的路，玩家除了赶路没有理由拐弯。宝箱是给"拐弯"一个回报。位置按地形特征扫描：**高处**（爬上去能俯瞰）、**水岸**（绕路才看得到）、**坡地**（顺路撞见）各挑一批——只挑一种的话玩家很快摸清规律，探索就变成打卡了。掉落用箱子序号做种子，同一个箱子每次开出同样的东西；已开启状态进存档，否则读档后满地图的盖子重新合上，玩家会以为进度没保存。

**敌人分了三层**。之前全场只有一种骷髅，打了十只之后玩家就摸清了"敌人"这个词的全部含义。三种之间不是单纯的数值缩放，而是逼玩家换打法：小兵垫节奏、战士血厚攻击慢（硬拼会亏血，得躲开前摇）、精英是"要不要打"的判断题。掉落也拉开档次，骨头是硬通货，精英额外掉向阳果。

祭坛守卫改成 2 小兵 + 1 战士的混编：清一色小兵会变成"砍三下、砍三下"的重复劳动，混一只战士，玩家得在乱战里分辨哪只的起手更长。

**骨头有了去处**。3 块骨头在贤者那里换 1 颗向阳果——不然打怪掉的东西只会在背包里堆积。

### 阶段 13：支线、打击感与音效

**支线任务**。主线是"世界要你做的事"，支线是"某个人要你做的事"——差别不在大小，而在**谁在说**。主线里贤者讲的是大陆的命运，支线里樵夫只关心自己的斧头。有这几句闲话，世界才不像一个只等你通关的布景。

两条支线刻意选了不同的玩法：樵夫要三块骨头（打怪），贤者要五个蘑菇（采集）。为此把蘑菇做成了可拾取物，掉落表也跟着调了——向阳果最稀有、蘑菇次之、野莓常见。

完成状态进存档，任务栏上方是主线、下方小字是支线（支线是"顺便做的事"，不该和主线抢同样的视觉权重）。

**打击感**。之前打完一场架，玩家只能从"敌人掉血了"推断自己打中了。三件事：

- **顿帧**：命中瞬间把世界时间压慢到 12%，持续 55 毫秒。画面短暂凝滞，大脑会把那一刻读成"撞上了硬东西"。短于 40 毫秒感觉不到，长于 80 毫秒会让连招发黏。UI、存档计时、相机仍走真实时间——否则血条跟着卡一下，那看起来像掉帧而不是打击感
- **受击闪白**：原来是闪红，但暗红在绿草地上看着像"敌人身上着了火"。白色是纯粹的受击信号，数值给到 2.6（HDR），走 ACES 后仍然扎眼
- **命中火花与挥砍轨迹**：击中点的扩散圆环 + 剑扫过的一道弧光，给攻击一个"体积"

**音效**。全部用 Web Audio 现场合成，不加载任何音频文件——没有声音对动作游戏是致命的，但这一版也没有音效素材。合成的好处是改起来快：调一个数字换音色，不用管授权。挥剑是带通滤过的白噪声从高扫到低，命中是低频方波加一点噪声（碰撞的"实"来自低频），拿封印是一段上行琶音。

AudioContext 在用户第一次交互前是挂起的，所以解锁挂在真实手势事件上，不能靠定时器。

**电元素**。按 T 放电，但**必须站在水里**——电流顺着水面走，岸上的敌人不受影响。这条限制是刻意的：电击范围大、伤害高，代价就是得先把敌人引到水边，而不是随时能按的万能键。

到这里水火冰电四者的关系闭合了：火怕水（往水边跑能切断火线）、冰封水面（搭桥）、电靠水（水面导电）。同一个战场上的取舍。

### 阶段 14：闪避与风元素

**闪避**。按 Q 翻滚，位移约 3.7 米、0.35 秒，**前半段有无敌帧**。无敌只覆盖前半段是刻意的——全程无敌会让玩家把它当免费位移用，而不是"看准了再躲"。只在地面可用：空中闪避会让跳跃的读秒失去意义，玩家可以一路闪现过悬崖。

速度曲线用二次衰减：起步最快然后迅速收住。线性衰减的尾巴太长，看起来像"滑出去"而不是"闪一下"。速度值要按「位移 = 速度 × 时长 / 3」倒推（二次衰减的积分是 1/3）——这一点第一次写错了，给了 13，实际只滑出 1.5 米，还不够躲开一次攻击的前摇。

**风元素**。按 V 起风：吹散周围的火焰，滑翔时给自己一个水平推力（从山顶起跳、半路来一阵风，能多滑很远）。至此四元素闭合：**火烤化冰、冰封水面、电靠水导电、风吹灭火焰**——同一个战场上四者互相牵制，每次交手都要判断该用哪个。

### 阶段 15：武器、野兽与烹饪

**武器系统**。塞尔达式循环的三根支柱：**捡、换、碎**。野外插着发光的武器（光柱颜色即稀有度），走近自动拔起；数字键 1–4 直选；每次命中耗 1 点耐久，归零当场碎裂并自动切下一把。六种武器（树枝/匕首/单手剑/手斧/双手剑/战斧）在伤害、攻速、范围上各有权衡——匕首 0.38 秒出手但只伤 1，战斧 0.95 秒才抡完但一斧 5 点。

武器挂在角色的 `handslot.r` 骨骼上。两个坑：一是 GLTFLoader 会剥掉骨骼名里的点号（`handslot.r` 变成 `handslotr`），按原名找永远找不到；二是 KayKit 角色模型的挂点下**自带一整套隐藏的武器网格**（Knife、Crossbow 等），不藏起来玩家手里会同时握着两把刀。换武器会打断进行中的攻击——否则命中帧会拿新武器的参数去结算旧武器发起的挥砍。

**拟人挥舞**。连续出招时三段连击轮换动画（下劈→斜削→横扫），动画按武器招式组分三套（单手劈砍/双手抡/突刺），时长跟随武器——大剑慢、匕首快。

**野兽**。鹿、雄鹿、狐狸、狼用 Quaternius 的带动画模型（吃草/疾跑/攻击/死亡全套），野猪和兔子程序化拼装（四腿对角步态、耳朵随状态竖贴）。行为是台小状态机：吃草 → 警觉（抬头看一眼，这一下停顿是"活物"的关键）→ 逃跑；狼和野猪例外，它们反过来追你。离玩家 120 米外的动物冻结，但尸体例外——打猎回来肉应该已经化好，而不是尸体被冻结在半空。强敌（精英骷髅）倒地时会把生前用的双手武器插在尸体旁。

**篝火烹饪**。营地加野外共五处火堆，锅边按 E 开火：点选最多 3 样食材下锅，界面实时预览产物。配方不列表格让玩家背，而是几条直觉规则：肉+蘑菇=肉菇串、纯肉=烤肉串、水果们=拼盘、向阳果下锅=阳光炖菜（回满）、剩下统统大杂烩（也比生吃划算）。做饭时世界不暂停——做饭不该是安全屋。

**修掉的视觉事故**。命中火花和斩击轨迹初版给了 HDR 3 左右的亮度，配上 bloom 后一次命中就是一颗糊住半个屏幕的光球；敌人受击闪白的 emissive 2.6 倍同样被拉成人形光雾。最终收敛到：火花 HDR 1.7、环径约 1 米，闪白 emissive 1.05——**走 bloom 的发光体，亮度过 2 就要小心**。斩击轨迹的海拔也跟着修了一刀：原来 y 固定写死，山上挥剑时轨迹沉到地面下二十米。

### 阶段 16：群系分区

用户原话是"到处都是草地，场景就很奇怪"。根因是地貌只有一个维度（海拔），同一海拔走到哪里都一个样。加了第二个维度——**区域噪声**（约 220 米一个特征尺度），把草原带再细分成开阔草甸、密林、秋色林三块；海拔继续管沙滩/岩石/雪顶。

三处从同一个 `biomeAt()` 读群系，各写各的就会对不上（地上金黄、树却绿着）：

- **地形顶点色**：秋色区地面染成落叶金黄，密林地面压深（树冠遮阴），过渡带用两条 smoothstep 渐变，没有硬边
- **草地**：草甸茂密鲜亮、秋林稀疏枯黄（落叶盖住草）、高地石缝零星几丛、沙滩雪顶寸草不生
- **散布物种**：落叶树加了秋色亲和度——秋林里权重 ×8 压倒性主导，出了秋林压到 6%。"秋林就该成片，不该满地零星几棵"

### 阶段 17：神庙与心之容器

四座露天试炼场守在四个方向（晨曦/落霞/听涛/凌峰），光柱冲天、老远可见，小地图上也有标记（青色三角，通关转金）。站上中央石台触发试炼：四角升起封印光柱，三波守卫（小兵→战士→精英）依次现身；全灭后中央升起祝福宝箱——**心之容器（生命上限 +1，顺手回满）+ 一把史诗武器**。神庙进度入存档，读档回来的神庙奖励视为已领，防止无限刷心。

结构上复用现有的一切：敌人走 EnemyManager 的定点刷怪（新增 `spawnAtPositions`），守卫的活动范围锁死在神庙周围；宝箱视觉与开箱交互跟野外宝箱同一套手感。不做室内副本——副本是另一张地图，成本十倍，而"光柱 → 挑战 → 祝福"的核心循环完全相同。

### 阶段 18：战斗的最后一公里

**完美闪避（Flurry Rush）**。敌人攻击落下的那一帧玩家正在闪避无敌帧里 → 子弹时间 1.6 秒：世界压到 0.28 倍速，玩家保持原速——`playerDt` 和 `worldDt` 两条时间轴分开走，敌人慢动作里你能反打一整套。配一声清亮钟音和屏幕边缘的蓝色暗角，这个奖励窗口必须"读得出来"。

**蓄力旋风斩**。按住攻击键半秒自动放出：360° 横扫、伤害 1.8 倍、击退加重，动画用双手抡圈。这里踩了一个时序坑：按下瞬间普攻已经出手（手感要求），蓄力到点时普攻还在收招——第一版"松手取消待发"，结果重武器普攻 0.85 秒收招，玩家等不到就松手，旋风斩永远放不出来。改成到点后留 0.9 秒待发窗口，手一空就放。

**爬空气修复**。之前对着空地走也会突然开始攀爬：触发条件只有"附近有柱子 + 朝向夹角 60° 内"，从两棵树中间穿过都会被吸住。真正的判据是**这一帧确实被障碍物顶住了去路**（碰撞推出把位移顶了回来），再把朝向锥收到 41°——没被挡住就谈不上"抱住柱子"。

**野生动物穿树**。野兽移动原来没有障碍物碰撞，野猪撞人直接穿过树干。和玩家接同一个 `ObstacleGrid.resolve`，一根柱子都穿不过去了。

### 阶段 19：手工规划的地图

用户说"地图太乱了"——根因是纯噪声生成，没有"目的地"这个概念。现在噪声只管区域内的细节起伏，宏观格局由手工规划的五个区域定：

```
        北 · 苍雪峰（70m+，雪顶）
        西 · 风啸高原（47m 台地）   东 · 低语森林（谷地，内嵌秋色林）
        中央 · 初心平原（18–26m，出生点/营地）
        南 · 明镜湖（压到水下 5m 的大湖，湖心岛上有冰祭坛）
```

各区域用 80–120 米宽的过渡带向目标高度 lerp，平原来回雪山必然路过高原坡地，不会有一道悬崖把地图切开。群系判定跟着区域走而不是纯噪声：秋林只在东部谷地内成片。

**道路网络**。营地出发通向三座祭坛与封印之门。折线路径在每个顶点混入土色、草稀、树避让——三方读同一个 `RoadNetwork.distance()`。路必须在世界装配**之前**建好（散布是同步的，树落地就不挪），所以 main 里先用同种子高度场扫出祭坛选址、修好路，再装世界。祭坛文案也按真实方位写："沿南边的路到明镜湖"。

**区域标题**。走进新区域时地名从屏幕下方浮出来（苍雪峰/明镜湖/低语森林/风啸高原/初心平原）——区域要成为玩家心智地图的一部分，就得把名字说出来。

### 阶段 20：盾牌与格挡

角色背上多了一面圆盾（平时背着，是塞尔达式的经典剪影），**右键举盾格挡**：正面 70° 内的攻击完全免伤，配一声金属脆响；代价是移动变慢、不能攻击——格挡是被动的坚守，不是免费的无敌。侧后方的攻击挡不住，所以格挡时面朝威胁是操作含量所在。技术上盾在 chest 骨骼（背后）和 handslot.l（左手）两个挂点之间切换。

### 阶段 21：弓箭与料理增益

**猎手弩**。武器袋里的远程招式：装备后左键放箭，combat 照常进入 attacking（驱动拉弦动画），但近战扇形被关掉——命中由箭矢的抛物线轨迹结算。箭是池化的 InstancedMesh，抛物线初速 34 m/s、重力 12，下坠要靠"抬高一点"补偿。弹药是全武器共享的箭数池（塞尔达的箭就这样），箭捆是武器点里的"伪武器"，捡起来 +5。弩也耗耐久，24 发散架。一个射角教训：**第三人称的相机俯角不能拿来当箭的仰角**——默认 0.32 的俯视会把箭直接压进脚边的地里，射角固定小仰角，瞄准交给重力与直觉。

**料理增益**。好食材做出的料理除了回血还带限时增益，挂点在两处：攻击倍率走 `combat.damageMultiplier`（武器数据不动），防御倍率在 `onDamagePlayer` 入口打折。阳光炖菜 = 完全恢复 + 60 秒攻击 ×1.5，鲜肉蘑菇串 = 5 心 + 60 秒受伤减半。血条下方的 buff 条显示剩余秒数。

### 修掉的几个顽疾

**地面上的黑线（区块接缝）**。之前一直以为是裙边的问题——裙边是竖直面、接不到顶光，所以压暗。把裙边提亮、染红、改双面渲染，黑线纹丝不动；只有清空重建才消失。真正的根因是 **`computeVertexNormals()` 对区块边界顶点算出的是单侧法线**：它只累加块内三角形的面法线，于是相邻两块在同一条边界上各算各的，一边朝上、一边是斜的，光照在接缝处硬生生断开。改成**只依赖世界坐标的解析法线**（固定 2.5 米步长的中心差分，高度网格向外多采 4 圈供边界取用）之后，边界两侧必然算出同一个法线，接缝处的光照天然连续。

**启动时的间歇性测试失败**。素材加载一开始写成串行（先 56 个自然模型，再一个 4.8MB 的敌人骨架），启动路径被拉长，测试脚本偶尔在地形流式加载完成前就开始操作，表现为随机失败。改成 `Promise.all` 并行拉取即可——骨架那一个文件比全部自然素材加起来还大，串行等于把它的下载时间白加在启动路径上。

### 性能上的几个关键决策（改代码前先读）

这些都是在 M1 的预算下反复权衡的结果，改动前请先理解原因：

1. **地形顶点采样一次成形**。噪声采样很贵，逐顶点重复调用会让块重建从 10ms 涨到几百毫秒。所以先算整块高度网格，法线、坡度、配色全从网格读。
2. **每帧只重建有限个地形块**。块重建是同步的，给太多预算会在相机快速移动时掉帧。
3. **植被按区块烘焙成静态网格，而不是用 InstancedMesh**。InstancedMesh 一个批次只能装一种几何体，draw call 就等于「物种数 × 区块数」。两种手写树还能忍（2×16=32），换成外部素材后二十多种物种立刻变成三百多个 draw call。既然树生成之后永不移动，实例矩阵就是常量，索性把它烘焙进顶点：每个区块把范围内的所有物件（不分物种）变换到世界空间后合并成一个几何体，draw call 只等于区块数。
4. **采样用原始帧时间，显示用平滑值**。p95 和 max 的意义在于捕捉尖峰，用 EMA 平滑会把卡顿抹掉，报告就失去诊断价值。
5. **不用物理天空**。物理散射的亮度远高于 Lambert 地形，两者无法共用曝光值——迁就地形则天空过曝成灰白。风格化渲染要的是可控调色。
6. **`renderer.info.autoReset = false`**。EffectComposer 每帧调用多次 `render()`，自动重置会让统计永远只剩最后一个全屏 pass 的数据（表现为 draw call 恒为 1）。
7. **火焰用 HDR 颜色，而不是 `material.toneMapped = false`**。项目走 EffectComposer，OutputPass 是个全屏后处理，它无从知道哪个物体该跳过色调映射——`toneMapped = false` 在这里不生效。所以火焰的红色分量给到 3 以上来对抗 ACES 的去饱和，顺带因为亮度超过 bloom 阈值而自带光晕。第一版用普通橙色，渲染出来是一片米黄色锥体，完全不像火。

### 跑测试请用生产构建，不要用 dev server

```bash
cd client && npm run build && npm run preview   # 服务在 4173
node tools/verify_player.mjs "http://localhost:4173/?hour=12&freeze=1"
```

**这一条是踩过坑才写下的**：dev server 开着 HMR，脚本改动源码后会立刻把更新推给正在被测试的页面，页面一重载，`window.__monitor` 之类就全空了，表现成"跑到一半突然所有断言失败、查询超时"。当时排查了很久才意识到不是游戏的问题。生产构建没有 HMR，结果才稳定。

### 其它注意

- 脚本通过 CDP 驱动 headless Chrome，用**真实时间**等待。不要用 `--virtual-time-budget`——虚拟时钟推得太快，而游戏逻辑依赖 rAF 的真实时间轴（详见 `tools/lib/cdp.mjs` 的注释）。
- 每个 `evalJs` 都带 10 秒超时。没有超时的话，页面一旦卡住，Promise 永不 resolve，脚本会静默挂死、连报错都没有。
